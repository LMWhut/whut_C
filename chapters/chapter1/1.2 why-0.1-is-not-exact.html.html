01

计算机为什么只认识 0 和 1？

计算机内部是无数个电子开关（晶体管），它们只有两种稳定状态：

  • 通电 / 高电平 —— 记作 1
  • 断电 / 低电平 —— 记作 0

用两种状态表示数据最可靠、最不容易出错。于是整个计算机世界的一切——数字、文字、图片、视频——最终都被拆成一串 0 和 1。

一个 0 或 1 叫一个「比特（bit）」。8 个比特组成 1 个「字节（Byte）」。 本课要讲的单精度浮点数，占 32 个比特 = 4 个字节。
02

二进制与十进制：其实就是「位权」不同

我们平时用十进制，是因为「逢十进一」，每一位的权重是 10 的幂：

1234 = 1×10³ + 2×10² + 3×10¹ + 4×10⁰
     = 1000  + 200   + 30    + 4

二进制「逢二进一」，每一位的权重变成 2 的幂：

1011₂ = 1×2³ + 0×2² + 1×2¹ + 1×2⁰
      = 8    + 0    + 2    + 1  = 11₁₀

整数部分：各位的权重

位置2⁷2⁶2⁵2⁴2³2²2¹2⁰
权重1286432168421

小数部分：权重继续往右「除以 2」

位置2⁻¹2⁻²2⁻³2⁻⁴2⁻⁵…
权重0.50.250.1250.06250.03125…
关键结论：二进制小数能表示的最小「步长」是 0.5、0.25、0.125、0.0625…… 它们是 2 的负整数次幂。这个事实，是后面一切问题的根源。

05

动手算 0.1 —— 结果停不下来了

现在用同样的方法算 0.1：

步骤计算取整数位剩下的小数
10.1 × 2 = 0.200.2
20.2 × 2 = 0.400.4

0.1₁₀ = 0.000 1100 1100 1100 1100 1100 …₂

          ↑      └──── 循环节 "0011" 永远重复 ────┘
0.1 在二进制里是一个无限循环小数。就像十进制里的 1/3 = 0.333333… 永远写不完一样。
06

计算机怎么存小数：IEEE 754 单精度格式

既然算不完，计算机只能存一部分、剩下的丢掉。但怎么存才科学？答案是用类似「科学计数法」的方式。

32 位（单精度 float）被划分成三段：

0
01111011
10011001100110011001101
符号位 1 位 指数位 8 位 尾数位 23 位
部分位数作用
符号位 S10 表示正数，1 表示负数
指数位 E8决定小数点的位置（数量级）
尾数位 M23决定有效数字（精度）

下面我们把 0.1 一步步「塞」进这 32 个格子里。

07

第 ① 步：写成二进制的「科学计数法」

十进制里我们会把 1234 写成 1.234 × 10³。二进制里也一样，把小数点移动到第一个 1 的后面：

原始：  0.0001100110011001100110011…₂
              └──── 小数点右移 4 位 ────┘
结果：  1.1001100110011001100110011…₂ × 2⁻⁴
        └┬┘                          └┬┘
      只有一个 1                   指数是 -4
为什么要这样写？因为规范化的二进制数，整数部分永远是 1（只要不是 0）。 既然永远都是 1，那就不用存了！这就是「隐含的 1」，白白省下 1 个比特。

所以我们现在手里有三个信息：

  • 符号：正数 → 0
  • 真实指数：-4
  • 有效数字：1.1001100110011001100110011…（这里的 1. 不用存）
08

第 ② 步：指数怎么存？—— 加 127 偏置

指数可能是负的（比如 -4），但指数位是 8 个纯 0/1，没有符号位。怎么办？

办法：统一加上一个固定的偏移量 127，把负数「搬」到正数区间。

偏置值 bias = 2⁸⁻¹ − 1 = 128 − 1 = 127

存入的指数 = 真实指数 + 127
           = (−4) + 127
           = 123

把 123 转成 8 位二进制：

123 = 64 + 32 + 16 + 8 + 2 + 1
    = 2⁶ + 2⁵ + 2⁴ + 2³ + 2¹ + 2⁰

位数：  2⁷  2⁶  2⁵  2⁴  2³  2²  2¹  2⁰
取值：   0   1   1   1   1   0   1   1
       └─────────── 01111011 ───────────┘
读取时反过来算：存储值 − 127 = 真实指数，即 123 − 127 = −4。
用 127 偏置，8 位指数可以表示真实指数范围 −126 ~ +127。
09

第 ③ 步：取 23 位尾数 —— 还要四舍五入！

有效数字是 1.1001100110011001100110011…，但尾数位只有 23 个格子，必须截断。

完整小数部分： 1.1001100110011001100110011 0011 0011 …
                 └──────── 取前 23 位 ────────┘└─ 第 24 位 ─┘

前 23 位：  10011001100110011001100
第 24 位：  1   ← 是 1，要「进位」！

进位后：    10011001100110011001101
这一步就是舍入误差的来源。如果第 24 位是 0，直接丢掉；是 1，就要向前进 1 位。 （IEEE 754 实际用的是「四舍六入五成双」，但这里刚好是进位的情况。）

转成十六进制：4 位一组

二进制太长不好写，程序员习惯每 4 位合成 1 个十六进制数字（因为 2⁴ = 16）。

0011  1101  1100  1100  1100  1100  1100  1101
  │     │     │     │     │     │     │     │
  3     D     C     C     C     C     C     D

所以： 0.1 的单精度十六进制 = 0x3DCCCCCD
二进制00000001001000110100…11011111
十六进制01234…DF

在 C / Java 里，0x3DCCCCCD 就是 float 类型的 0.1f 在内存中的原始比特。

12

再转回十进制，还等于 0.1 吗？

我们把存下来的值还原出来算一遍：

存储的值 = 1.10011001100110011001101₂ × 2⁻⁴

把它当成二进制小数展开：
= (1 + 0.5 + 0.0625 + …) × 0.0625

精确计算（用整数算最准）：
尾数位 = 10011001100110011001101₂ = 5033165
尾数整体 = 2²³ + 5033165 = 8388608 + 5033165 = 13421773

值 = 13421773 ÷ 2²³ ÷ 2⁴
   = 13421773 ÷ 134217728
最终结果：
0.1 在计算机里实际存的是
0.100000001490116119384765625
不是 0.1！差了大约 1.49 × 10⁻⁹。

这个误差很小，小到平时打印出来还是显示 0.1，所以你可能一直没发现。但它确实客观存在。

值
你写的0.100000000000000000000000000
计算机存的0.100000001490116119384765625
误差约 1.49 × 10⁻⁹
附：为什么这个精确计算可以用整数来算？

这里能“用整数算得准”，是因为 二进制浮点数的结构决定了它可以被写成一个整数除以 2 的幂，而“除以 2 的幂”在二进制里只是移动小数点，不会产生新的误差。我们一步步拆开看。

一、先看尾数是什么

0.1 规格化后是：

1.10011001100110011001101₂ × 2⁻⁴

尾数部分 1.10011001100110011001101 里：

  • 小数点左边是 1 位：1
  • 小数点右边是 23 位：10011001100110011001101

所以它一共是 24 位二进制有效数字。

二、把它变成整数：乘以 2²³

如果要让这个数变成整数，只需要把小数点 右移 23 位，也就是乘以 2²³：

1.10011001100110011001101₂ × 2²³
= 110011001100110011001101₂

这个 24 位二进制整数就是：

1 10011001100110011001101₂

把它拆成两部分看：

= 1 × 2²³  +  10011001100110011001101₂
= 2²³       +  10011001100110011001101₂

已知：

2²³ = 8388608
10011001100110011001101₂ = 5033165

所以：

1.10011001100110011001101₂ × 2²³
= 8388608 + 5033165 = 13421773

三、别忘了外面还有个 × 2⁻⁴

我们刚才算的是“尾数 × 2²³”，但真实值是：

尾数 × 2⁻⁴

为了保持相等，我们把刚才乘的 2²³ 再除掉：

值 = 尾数 × 2⁻⁴
   = (尾数 × 2²³) × 2⁻²³ × 2⁻⁴
   = 13421773 × 2⁻²³ × 2⁻⁴
   = 13421773 × 2⁻²⁷

所以：

值 = 13421773 ÷ 2²⁷

而：

2²⁷ = 134217728

因此：

值 = 13421773 ÷ 134217728

四、为什么这样算就是“精确”的？

关键在于两点：

1. 浮点数的尾数是有限位二进制

单精度尾数只有 23 位，所以它一定能写成一个“整数 ÷ 2²³”的形式。

1.10011001100110011001101₂
= 110011001100110011001101₂ ÷ 2²³
= 13421773 ÷ 8388608

2. 除以 2 的幂，在二进制里只是移动小数点

在十进制里，除以 10 的幂就是小数点左移：

1234 ÷ 10³ = 1.234

在二进制里完全一样，除以 2 的幂就是二进制小数点左移：

110011001100110011001101₂ ÷ 2²³
= 1.10011001100110011001101₂

这个操作 不会产生任何舍入误差，因为只是把小数点挪了位置，每一位数字都原样保留。

所以：

值 = 13421773 ÷ 2²⁷

这个除法在数学上是完全精确的，因为分子分母都是整数，而且分母是 2 的幂，结果是一个有限二进制小数。

五、和“直接用十进制小数算”有什么区别？

如果你直接写：

1.10011001100110011001101₂ × 2⁻⁴

然后想用十进制小数去算，会碰到两个麻烦：

  1. 二进制小数转十进制时，每一位权重是 0.5、0.25、0.125……这些数在十进制里虽然有限，但加起来容易算错；
  2. 中间步骤如果用十进制浮点数计算，本身又会引入新的舍入误差。

而用整数算：

13421773 ÷ 134217728
  • 分子分母都是精确整数；
  • 分母是 2 的幂，二进制意义下“除得尽”；
  • 不涉及任何近似。

所以这个结果就是计算机里 实际存储的那个浮点数所代表的精确十进制值：

13421773 ÷ 134217728
= 0.100000001490116119384765625

六、一句话总结

单精度浮点数的尾数只有 23 位，所以它可以写成 整数 ÷ 2²³；
再乘上指数 2⁻⁴，就变成 整数 ÷ 2²⁷。
除以 2 的幂在二进制里只是移动小数点，不产生误差，
所以用整数来算，得到的就是那个浮点数真正代表的精确值。

这就是为什么可以用整数精确计算，而不是近似计算。

13

为什么有的小数就是存不下？

回到最根本的问题。二进制小数的权重是：

0.5   0.25   0.125   0.0625   0.03125   …

它们全都是 1/2ⁿ 的形式。两个这样的数相加，结果的分母仍然是 2 的幂。

也就是说：能用有限位二进制精确表示的小数，其分母（约分后）只能是 2 的幂。

十进制数最简分数分母含因子能否精确存储
0.51/22✓ 可以
0.251/42✓ 可以
0.6255/82✓ 可以
0.11/102 × 5✗ 不行
0.21/55✗ 不行
0.33/102 × 5✗ 不行
类比一下：在十进制里，1/3 = 0.3333333… 永远写不完，因为我们只有 10 个数字，除不尽 3。
同样地，在二进制里，分母含有因子 5 的数，永远除不尽。
不是计算机「算错了」，是 0.1 这个数本身在二进制下就是无限循环的。

终极问题：为什么 0.1 + 0.2 ≠ 0.3？

在 Python 或 JavaScript 的控制台里敲下这一行：

>>> 0.1 + 0.2
0.30000000000000004

这不是 bug，也不是语言的问题，而是所有遵循 IEEE 754 标准的计算机都会这样。

说明：日常编程（Python / JavaScript / Java 的 double）默认用双精度（64 位，尾数 52 位）， 原理和上面讲的一模一样，只是位数更多、误差更小。下面用双精度来看。

原因拆解

  1. 0.1 存进去时就已经不是 0.1 了 
    真实存储： 0.1000000000000000055511151231257827…
  2. 0.2 存进去时也不是 0.2 
    真实存储： 0.2000000000000000111022302462515654…
  3. 两个「近似值」相加 
    0.1000000000000000055511151231257827…
+ 0.2000000000000000111022302462515654…
─────────────────────────────────────────
= 0.3000000000000000166533453693773481…   ← 精确和
  4. 这个和又要存进 64 位里，还得再舍入一次 
    舍入后的结果： 0.30000000000000004440892098500626…
显示出来就是： 0.30000000000000004
  5. 而 0.3 单独存进去，是另一个值 
    0.3 实际存储： 0.29999999999999998889776975374843…
结论： 
0.1 + 0.2  →  0.30000000000000004…
     0.3   →  0.29999999999999998…

两者不相等  →  0.1 + 0.2 ≠ 0.3

误差在每一步「存储」和「运算」中一点点累积，最后就暴露出来了。

16

总结与避坑指南

三个核心结论

  1. 二进制小数的权重是 1/2、1/4、1/8…，只有分母为 2 的幂的分数才能被精确表示。
  2. 0.1、0.2、0.3 这类数在二进制下是无限循环小数，计算机只能存一个「最接近的近似值」。
  3. 浮点数运算会累积误差，所以不能用 == 直接比较两个浮点数。

编程中的正确做法

场景❌ 不要这样✅ 应该这样
判断浮点数相等 a == b abs(a − b) < 1e-9

或 Decimal
输出显示 直接打印 格式化保留 2 位小数
一句话记住：
计算机不是「算不准」，而是它用二进制工作，而 0.1 这个数在二进制里本来就没有尽头。
就像我们没法用十进制写完整 1/3 一样。
